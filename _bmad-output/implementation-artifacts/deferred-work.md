## Deferred from: code review of 1-2-real-generation-request (2026-08-01)

- No client-side timeout/`AbortController` on the `/loading` page's `/api/generate` fetch (`web/app/loading/page.tsx:45-73`) — AC4 explicitly lists "times out" as a failure mode requiring an explicit failure state, but the current implementation only handles non-2xx responses and thrown/network errors; a request that never resolves leaves the loading page frozen at 100% forever. Zero live risk today because `getModelClient()` only ever returns the deterministic, fast mock client — the real Anthropic adapter isn't wired in yet (per project context). Add an `AbortController`-based timeout (duration TBD, likely tied to whatever real-world latency budget the real adapter ends up needing) as part of whichever story wires in the real Anthropic client (Phase 4a), rather than reopening this story now.
- `web/lib/store/generationStore.test.ts` imports `lib/ai/generateVocalChain` and `lib/ai/mockModelClient` directly, in literal (not spirit) tension with Architecture AD-9's wording ("only `app/api/generate/route.ts` may import from `lib/ai/*`"). Deliberate choice per this story's Dev Agent Record (avoids a fragile hand-fabricated fixture that could drift from the real nested schemas) and poses no real risk since test code never reaches the client bundle. Worth a small wording tweak to AD-9 in a future architecture-doc pass to explicitly exempt test files, rather than a code change.
- React Strict Mode (on by default for the App Router since Next.js 13.5.1, unconfigured/default in this project) double-invokes `loading/page.tsx`'s fetch effect in development, firing two real `/api/generate` POSTs per page load in dev mode only. Production builds don't double-invoke, so there's no user-facing impact today. Once the real Anthropic adapter replaces the mock client, this will double local dev-testing cost/latency per page load — worth adding an idempotency guard (e.g. a ref-based "already fired" flag) at that point.

## Deferred from: code review of 1-3-plugin-visual-component (2026-08-02)

- `invert` prop on `NumberArcKnob` (`web/app/components/controls/PluginKnobPrimitives.tsx`) is dead/untested code — built specifically for DeEsser 2's Max Reduction dial, but that component bypasses it via a hand-computed `ArcKnob` + `invertedKnobRotationDeg(...)` call instead. Zero real-world coverage of the `invert` branch (including its min/max label-swap logic). Either wire DeEsser 2's Max Reduction through `NumberArcKnob { invert }` for real coverage, or remove the unused prop.
- `channelEqCurve.ts`'s `GAIN_TICKS`/`GAIN_LABELED` (`web/lib/eq/channelEqCurve.ts:242-243`) include values down to -60dB, but `dbToY()` is linear only across ±15dB onto the plot's actual pixel span — any tick below -15dB computes a y-coordinate far outside the SVG viewBox and never renders. Leftover dead constants from the removed "two-slope" axis model. Trim both sets to the real ±15dB range whenever this file is next touched.
- `ChannelEqVisual.tsx` and `PitchCorrectionVisual.tsx` each hand-roll their own card+header markup (border/rounded-corner/shadow/header structure) instead of using the shared `PluginPanel` from `PluginKnobPrimitives.tsx`, which the other 8 knob-based visuals all use — three near-identical copies of the same chrome, against the project's own "don't duplicate UI" principle. Checked how close the fit actually is before deferring further (2026-08-02): Channel EQ maps onto `PluginPanel` almost exactly (`width: "1000px"` only, header `px-6 py-4` — identical to `PluginPanel`'s hardcoded default), genuinely low-risk to migrate. Pitch Correction does not: its header is `px-6 py-3`, one size down from `PluginPanel`'s hardcoded `py-4`, and Pitch Correction is the component with the deepest pixel-QA history of all 10 (7 sub-rounds, see its Dev Agent Record entries). A mechanical migration would either silently regress that verified spacing or require first adding a header-padding override prop to `PluginPanel` (and confirming py-3 is actually still correct against the reference, not just an old inconsistency) — not a drive-by change. Channel EQ's half could reasonably be done alone; Pitch Correction's needs its own dedicated pass with re-verification.
- `formatKnobValue`'s per-parameter display overrides (`"ratio"`, `"drive"`, `"output"`, `"rate"`, `"intensity"`, `"decay"`) are matched by bare parameter name with no plugin scoping, shared globally across all 8 knob-based plugins. A future plugin registering a control with one of these exact names but a different real display convention would silently inherit the wrong formatting. No current collision exists. Consider scoping by `(pluginId, parameter)` if/when a collision actually surfaces.
- Three parallel log-scale implementations exist with different signatures/defaults: `logFraction` in `PluginKnobPrimitives.tsx` (hardcoded `1e-6` epsilon), a second `logFraction` in `PhaserVisual.tsx` (configurable epsilon, needed because Rate 1/2's 0-10Hz range needs a much bigger floor than `1e-6` provides), and the angle-domain `logKnobRotationDeg` in `knobRotation.ts`. A fix to the underlying log-scale-with-floor approach in one won't propagate to the others. Worth consolidating into one shared helper if a fourth use case ever needs the same idea.
- `resolveChannelEqBands`'s `resolveNumber` helper (`web/lib/eq/channelEqCurve.ts:51-57`) defaults an unresolved control value (including Q) to 0 if the registry definition itself somehow lacks a numeric default — a resolved `q=0` divides by zero in `biquadCoeffs`'s `alpha = sinw0/(2*q)`, propagating NaN through that band's whole curve response. Not currently reachable: every Channel EQ band's Q has a real registry default, and any live-Generation value is clamped to the control's registered min/max by `validateAndRepairChain` before this component ever sees it (this project's documented convention: "callers never re-validate `ModelClient` output"). Flagging because the component itself has no independent defense — relevant if this component is ever driven by hand-written data that bypasses the validation pipeline (e.g. a future test).
- The 24dB/Oct cut-band model (`web/lib/eq/channelEqCurve.ts`'s `cutBandResponseDb`) cascades two identical 12dB/Oct biquad stages at the same Q, rather than the differing per-stage Qs a real 4-pole (e.g. Butterworth) filter design would use. Internally consistent with its own tests (correctly doubles the dB at any given frequency far from cutoff) and a deliberate, already-documented choice in this story's own Dev Notes — but the curve's exact shape right at the cutoff knee won't perfectly match Logic's real 24dB/Oct response. Revisit if a future pixel-comparison against the reference ever specifically targets Band 1/8's cutoff knee shape.
- `niceTickValues` (`web/lib/controls/knobTicks.ts`) rounds every generated tick to 3 decimal places — fine for every control range currently in the registry, but would silently collapse distinct tick values to the same number for any future control registered with a sub-0.001-wide range. No current control is affected; nothing in the type system prevents one from being added later without revisiting this.
- `toneCurveY` (`web/lib/eq/overdriveResponseCurve.ts`) only clamps its lower bound (`Math.max(-1, db / TONE_DB_SPAN)`) despite its own comment describing `TONE_DB_SPAN` as the clamp span for the full normalized `[-1, 1]` range. Currently inert — a lowpass filter response never exceeds ~0dB passband gain — but the upper-bound guarantee the comment claims isn't actually enforced in code. Add the matching `Math.min(1, ...)` for defense-in-depth whenever this file is next touched.
- The bipolar knob fill's "zero" position (`web/app/components/controls/PluginKnobPrimitives.tsx`, `arcKnobRotationDeg((min + max) / 2, min, max)`) assumes the control's range is symmetric around zero. True for every bipolar control actually wired up today (Flanger's Feedback -100..100, Tape Delay's Clip Threshold/Spread, both symmetric) but not enforced — a hypothetical future asymmetric bipolar range (e.g. -10 to 30) would silently start its fill from the arithmetic midpoint instead of the true zero point.
- DeEsser 2's PRD §8.9 rule (Threshold/Max Reduction/Frequency always render at Logic's own defaults, never real per-song generated values) is enforced only by the fact that `DeEsser2Visual`'s function body never reads its declared `values: ControlValue[]` prop — confirmed correct by reading the full file, but nothing beyond a code comment stops a future edit from "fixing" this to read live data like every sibling knob-based component does, re-introducing the exact false-precision problem PRD §8.9 exists to prevent. Consider a type-level or lint-level guard if this component is touched again.
- `numericTicks`' `exclude` option (`web/app/components/controls/PluginKnobPrimitives.tsx`) filters via exact value equality (`options.exclude!.includes(v)`) rather than a floating-point tolerance. Currently safe — the only caller, Compressor's Make Up dial, excludes a clean integer (`40`) that `niceTickValues` also generates as an exact integer — but would silently fail to exclude a tick if a future caller's excluded value doesn't exactly match the generated float.

## Deferred from: code review of 1-4-results-page-real-chain (2026-08-02)

- In-memory `generationStore` (module-level `Map`, `web/lib/store/generationStore.ts`) won't survive a `GET /api/generate/[id]` landing on a different server instance than the `POST /api/generate` that saved the generation (serverless/edge/multi-worker deploys) — a just-created generation could 404 on the very next request. Pre-existing from Story 1.2, whose own Dev Notes explicitly authorize "in-memory is correct for now" as an architecture-level deferred decision; Story 1.4 only depends on it (its new `GET` route reads from the same store), it doesn't introduce the limitation. Revisit alongside whichever future story adds real persistence.
- Same store has no TTL or eviction path — every successful generation is added and never removed, so memory grows for the lifetime of the process. Same pre-existing Story 1.2 architecture decision as above.
- No `aria-live`/`role="status"` announcement on `results/page.tsx` or `loading/page.tsx` for loading/error state transitions — both use plain `<p>` elements, so a screen reader won't proactively announce "loading" → "ready"/"error" transitions. Matches the existing pattern already present on `loading/page.tsx` since Story 1.2, not newly introduced by this story, and no design-system/architecture doc currently mandates it. Worth revisiting as a small accessibility pass once the app's a11y bar is explicitly defined.
- An empty `chain.plugins` array has no dedicated handling in `results/page.tsx` — the page would render a "successful"-looking page with the heading/artist line but no plugin cards and no messaging. Nothing in `chainSchema`/`pluginInstanceSchema` (`web/lib/schema/chain.ts`) guarantees non-emptiness, so this is really an upstream generation-pipeline invariant question (should the pipeline guarantee at least one plugin, or should the *page* guard against zero), outside this story's fetch/dispatch-wiring scope.
- Task 4's typography/spacing consistency pass was only partially applied to `loading/page.tsx` — the `<Link>` → `AnimatedButton` swap happened, but no heading/body-text sizing changes were made. Soft finding: the page has no true heading element to begin with (only a `text-lg font-medium ... sm:text-xl` phase-status line, already reasonably close to the landing page's body scale), so the practical gap is small. Worth a quick look if `loading/page.tsx` is touched again for an unrelated reason.
